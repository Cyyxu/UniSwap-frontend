## Context

Home页面的AI助手使用自定义的 `streamChat` 函数处理SSE流式响应。当前实现能够正确接收和显示AI的回复内容，但在流结束时无法正确识别后端返回的结束标记 `{"errorCode":0,"errorMsg":"操作成功",...}`，导致 `onDone()` 回调未被调用，`aiLoading` 状态保持为 `true`，输入框持续禁用。

**当前流程：**
1. 用户发送消息 → `setAiLoading(true)`
2. 后端返回流式数据：`data:文本` 格式
3. 流结束时返回：`{"errorCode":0,...}`
4. `streamChat` 函数未识别此结束标记
5. `onDone()` 未被调用 → `aiLoading` 保持为 `true`
6. 输入框持续禁用

**技术约束：**
- 不能修改后端返回格式（后端已部署）
- 需要保持与AIChat页面的兼容性（使用不同的API）
- 必须支持多种SSE格式（标准JSON和纯文本）

## Goals / Non-Goals

**Goals:**
- 正确识别后端的流结束标记 `{"errorCode":0,...}`
- 在流结束时立即调用 `onDone()` 回调
- 确保 `aiLoading` 状态正确清除，输入框恢复可用
- 兼容多种SSE事件格式（大写/小写type字段）
- 保持现有功能不受影响

**Non-Goals:**
- 不修改后端API返回格式
- 不改变AIChat页面的实现（已使用 `aiApi.stream()`）
- 不添加前端限流逻辑（后端已有限流）
- 不重构整个 `streamChat` 函数架构

## Decisions

### 决策1：在JSON解析逻辑中添加结束标记检测

**选择：** 在 `try-catch` 块的 `try` 部分，优先检测 `errorCode` 字段

**理由：**
- 结束标记是有效的JSON，应该在JSON解析成功后处理
- 优先级高于其他事件类型，确保及时退出循环
- 使用 `'errorCode' in parsed` 检测，避免误判

**替代方案：**
- 在 `catch` 块中处理：不合适，因为结束标记是有效JSON
- 在循环外处理：太晚，可能导致额外的数据处理

### 决策2：兼容大写和小写的事件类型

**选择：** 同时支持 `type: "MESSAGE"/"DONE"/"ERROR"` 和 `type: "token"/"done"/"error"`

**理由：**
- 不同的后端实现可能使用不同的命名约定
- 增加兼容性，减少未来的维护成本
- 代码量增加很少，但鲁棒性大幅提升

**实现：**
```typescript
if (parsed.type === 'MESSAGE' || parsed.type === 'token') { ... }
if (parsed.type === 'DONE' || parsed.type === 'done') { ... }
if (parsed.type === 'ERROR' || parsed.type === 'error') { ... }
```

### 决策3：使用 `return` 立即退出循环

**选择：** 检测到结束标记后，调用 `onDone()` 并立即 `return`

**理由：**
- 确保不会处理结束标记之后的任何数据
- 立即触发状态更新，输入框快速恢复
- 避免不必要的循环迭代

**流程：**
```typescript
if ('errorCode' in parsed) {
  console.log('[Stream] 收到结束标记:', parsed)
  onDone()
  return  // 立即退出
}
```

### 决策4：保留循环结束后的 `onDone()` 调用

**选择：** 在 `while` 循环正常结束后仍然调用 `onDone()`

**理由：**
- 作为兜底机制，处理没有明确结束标记的情况
- 确保在任何情况下都能清除loading状态
- 不影响正常流程（因为已经 `return` 的情况不会执行到这里）

## Risks / Trade-offs

### 风险1：结束标记误判
**风险：** 如果后端返回的其他JSON数据也包含 `errorCode` 字段，可能被误判为结束标记

**缓解措施：**
- 检查 `errorCode` 字段的存在性，这是后端统一响应格式的标准字段
- 添加日志输出，便于调试和追踪
- 如果发现误判，可以添加更严格的检测条件（如同时检查 `errorMsg` 字段）

### 风险2：与AIChat页面的实现差异
**风险：** Home页面和AIChat页面使用不同的流式处理实现，可能导致行为不一致

**缓解措施：**
- 两个实现都已经过测试，功能正常
- 未来可以考虑统一使用 `aiApi.stream()`，但不在本次修复范围内
- 在文档中明确说明两种实现的差异

### 权衡1：代码复杂度 vs 兼容性
**权衡：** 添加多种格式支持增加了代码复杂度

**决策：** 接受适度的复杂度增加，换取更好的兼容性和鲁棒性
- 代码增加约20行，但可读性仍然良好
- 减少未来因格式变化导致的bug
- 通过注释和日志保持代码可维护性

### 权衡2：立即退出 vs 继续处理
**权衡：** 检测到结束标记后立即退出，可能丢失后续数据

**决策：** 立即退出是正确的选择
- 结束标记之后不应该有更多数据
- 如果有数据，说明后端实现有问题，应该在后端修复
- 快速响应用户操作比处理异常数据更重要
